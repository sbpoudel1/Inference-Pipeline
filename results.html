Phase 3 — The counterintuitive benchmark

The benchmark methodology

  • Image: DSC07061.JPG (6000×4000). The model resizes to 320×320 internally.
  • Hardware: Apple M-series, macOS 26.4, CPU only.
  • Scope: only the model forward pass is timed. Image decoding and preprocessing happen once, before the timer.
  • Warmup: 3 runs discarded.
  • Measure: 30 timed runs per backend.

Why this happened — and why the result is actually a win

The tutorial-blog narrative says "ONNX makes things faster, quantization makes things even faster." That's wrong on this hardware, and we have the numbers to prove it. Three concrete reasons:

  1. Apple Silicon arm64 favors PyTorch. Torch 2.x ships native arm64 kernels that go through Apple's Accelerate framework. ONNX Runtime's CPUExecutionProvider uses a generic CPU implementation that doesn't tap into Accelerate. The "ONNX is faster" claim holds on hardware ONNX was designed for: x86 servers, NVIDIA Jetson, ARM Cortex with INT8 silicon. Not Apple Silicon CPU.
  2. Dynamic INT8 quantization inserts conversion overhead. Every time an INT8 op feeds into a non-quantized op (and vice versa), runtime needs to convert. On a CPU without native INT8 acceleration, those conversion ops cost more than the INT8 math saves.
  3. Quantization erodes precision near thresholds. A borderline detection (score ~0.5) crossed the threshold and dropped out. Static quantization (with calibration data) would mitigate this; dynamic quantization can't.
The interview story this enables is much stronger than "I got a 2× speedup":
"I measured the canonical PyTorch→ONNX→quantized pipeline on my Apple Silicon laptop and found ONNX Runtime ran 50% slower than PyTorch, and dynamic INT8 quantization made it worse — and dropped a borderline detection. I can explain why: torch ships Accelerate-backed kernels that ORT's generic CPU provider can't match, and dynamic quantization adds quantize/dequantize overhead at layer boundaries on hardware without native INT8 support. The fix would be either ORT's CoreML execution provider, or static quantization with calibration data, or running the same pipeline on an x86 server or NVIDIA Jetson — which is the hardware ONNX was designed for. That's the next experiment."
That answer signals you read benchmark data, know there are platform-specific reasons quantization is/isn't a win, and can design follow-up experiments. It's much better than parroting a tutorial.

Phase 4 — Docker image

What got built

Multi-stage Dockerfile, 562 MB final image. Compare to what a naïve single-stage build with PyTorch in it would have produced: ~2 GB. The difference is the entire training stack — torch, torchvision, CUDA libs, sympy, networkx — none of which the inference container needs.

What's actually inside the runtime image:

  • python:3.12-slim base (~150 MB)
  • ONNX Runtime native libraries (~150 MB)
  • NumPy, FastAPI, Pillow, uvicorn (~100 MB)
  • The model files: detector.onnx (14 MB) + coco_classes.json
  • The application code (src/ + app/): a few KB

Smoke test

docker compose up, then a curl against the live container: 

$ curl -F "image=@data/samples/DSC07346.JPG" http://localhost:8000/predict

Identical detections (same labels, same scores to 4 decimal places) as the bare-metal CLI. Container latency was higher (738 ms vs 489 ms direct) — most likely due to Rosetta amd64 emulation on Apple Silicon. A native --platform linux/arm64 build target would close that gap.
