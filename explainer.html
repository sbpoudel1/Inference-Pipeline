1. The big picture

This project closes six resume gaps — computer vision, PyTorch, ONNX, ONNX Runtime, Docker, benchmarking — in one focused build, so you can speak credibly to the Symbotic MLOps role.

The arc, in one diagram:

PyTorch model  →  ONNX export  →  Optimized + quantized ONNX  →  FastAPI in Docker
   (Phase 1)       (Phase 2)            (Phase 3)                    (Phase 4)
                                            ↓
                                     Benchmark numbers
                                  (the interview artifact)

In plain English: take a model that someone already trained, convert it into a format that can run anywhere, make it faster, wrap it in a tiny web service, put that service in a box that can ship to any machine, and measure how all of this performs honestly. That's what an MLOps engineer does for a living.

3. Phase 1 — Baseline (the PyTorch model)

Goal: get a pretrained object detector running on real images locally. Confirm it produces sensible bounding boxes.

What we used

SSDLite320 with a MobileNetV3-Large backbone, pretrained on COCO. Decoded:

  • SSDLite — Single Shot Detector, "Lite" variant. Fast, small.
  • 320 — input image size in pixels (the model resizes everything to 320×320 internally).
  • MobileNetV3-Large — the convolutional backbone that extracts features. Designed for mobile/edge use.
  • COCO — the dataset it was trained on. 80 everyday object classes (person, car, dog, bench, etc.).

The three files

src/inference/model.py — one function, load_detector(), that returns the model, its preprocessing transform, and the list of class names. The first call downloads ~14 MB of weights to ~/.cache/torch/hub/ and reuses them forever.

src/inference/predict.py — wraps the model in a clean function: predict(image_path) → list of detections. Each detection is a plain Python dict with label, score, and box. No PyTorch tensors leak out — that matters because in Phase 2 we swap the backend and the caller shouldn't have to change.

scripts/phase1_baseline.py — the driver. Loops over images in data/samples/, calls predict(), prints results, and saves a PNG with the bounding boxes drawn on the image.

4. Phase 2 — ONNX export and parity

Goal: convert the PyTorch model to a portable format (ONNX) that can run without PyTorch installed. Then prove the converted model still behaves like the original.

What ONNX is, in plain terms

ONNX (Open Neural Network Exchange) is a file format for neural networks. Think of it as a "PDF for models" — once you save your model as .onnx, anyone with an ONNX runtime can load and run it, no matter what framework they use. Python is no longer required to run the model. C++ can run it. Java can run it. A custom binary on a robot can run it. That portability is the whole point.

The two scripts

scripts/phase2_export_onnx.py uses torch.onnx.export(...) to do the conversion. Three subtle things matter here:

  • A wrapper module. The torchvision detector takes a list of tensors and returns a list of dicts. ONNX doesn't love that shape; we wrap it so the export sees a single-tensor input and three-tensor output (boxes, scores, labels).
  • Dynamic axes. We tell ONNX which dimensions can vary at runtime: image height/width, and the number of detections. Without this, the exported model is locked to whatever size we used during export.
  • Opset version. ONNX has an "instruction set" version (opset). We picked 17 — modern enough to have all the ops the model uses, old enough that every runtime understands it.

scripts/phase2_parity.py is the bug-catcher. It runs both backends on the same images and asks: do they produce the same number of detections? With the same labels? With scores agreeing to 3 decimal places? Boxes within 1 pixel?

Why this script is the interview-relevant part: ONNX export is a translation, not a copy. Operations can be replaced with near-equivalents. Floating-point math can be reordered. NMS (the "non-maximum suppression" step that picks the best box per object) can differ between implementations. The parity test is what tells you if any of that matters in practice. If it fails, debugging it is the kind of work that makes you valuable.

5. Phase 3 — Optimize and benchmark

Goal: make the model faster, and measure honestly how much faster.

Two optimization techniques

Graph optimization. The model's compute graph has redundancies. For example, a Conv → BatchNorm → ReLU sequence can be mathematically merged into a single fused operation. ONNX Runtime can do this automatically. It's pure graph surgery — same numerical output, fewer/faster operations.

Dynamic INT8 quantization. Model weights are normally stored as 32-bit floats. Dynamic quantization casts them to 8-bit integers. The file shrinks ~4x. Integer math can be faster than floating-point math on many CPUs. The trade is a small loss of numerical precision.

The phase produces three variants of the model, all sitting in models/:

  • detector.onnx — the original FP32 export
  • detector_optimized.onnx — same graph after ORT's optimization pass
  • detector_quantized.onnx — INT8 quantized weights

The benchmark

scripts/phase3_benchmark.py compares latency across four backends:

  1. PyTorch (the baseline)
  2. ONNX, no graph optimization
  3. ONNX, with graph optimization
  4. ONNX, INT8 quantized + graph optimization

It does 3 warmup runs (discarded — caches and JIT compilation need to settle) and then 30 measured runs. Reports median, p95, and p99 latency.

The actual numbers were surprising. See results.html → Phase 3.

6. Phase 4 — Containerize as a service

Goal: wrap the inference in a web service, package it in a Docker image, and confirm the image is small and self-contained.

The FastAPI service

app/server.py exposes two endpoints:

  • GET / — health check, returns {"status":"ok"}
  • POST /predict — accepts an image upload, returns JSON detections

The service imports only src/inference/predict_onnx.py. That file has zero PyTorch dependency — it uses onnxruntime directly. That's what makes the Docker image small.

Multi-stage Docker

The Dockerfile has two stages:

  1. Builder stage. Uses python:3.12-slim as base. Installs everything from requirements-inference.txt (no torch!) into a virtual environment. This stage contains pip's cache, build artifacts, etc.
  2. Runtime stage. Also python:3.12-slim base. Copies only the virtual environment and the application code from the builder. No pip cache. No build tools. No PyTorch.

The result: the deployed image contains only what's needed to actually serve predictions. The "training stack" (PyTorch, torchvision, CUDA libraries, sympy, etc.) is left behind in the builder stage and never ships.

That's the "no Python on the robot" lesson made literal. Symbotic's robots don't run PyTorch — they run a compiled runtime against an exported model. Our Docker image is the desktop equivalent of that production handoff.

8. Concepts that may be new to you

Why model.eval() matters

PyTorch models have two modes: training and eval. Some layers — BatchNorm and Dropout in particular — behave differently in each. In training, BatchNorm uses statistics of the current mini-batch; in eval, it uses the running statistics accumulated during training. Dropout randomly zeros activations during training and does nothing during eval. If you forget model.eval(), your predictions are silently wrong — not crash-wrong, just degraded-wrong. Classic PyTorch footgun; the kind of thing an interviewer might ask.

What "preprocess transforms" really do

A neural net was trained on inputs of a specific shape and value range. SSDLite was trained on 320×320 images with pixel values normalized to specific mean/std numbers. If you feed it a raw 6000×4000 JPG, the answer is garbage. weights.transforms() returns the exact resize+normalize pipeline used during training. Bundling this with the weights is a torchvision convenience that prevents a whole class of bugs.

Why pretrained weights at all?

We could train a detector from scratch on COCO. It would take many GPU-hours and add nothing to the resume bullet. The MLOps role is about handling models, not training them from scratch. Starting from pretrained mirrors the real workflow: an ML team hands you a model, your job is to make it run fast in production.

What ONNX Runtime actually is

A piece of software that loads an .onnx file and runs it. Written in C++. Has Python bindings (which is what we use). Has C, C#, Java, JavaScript bindings too. Can target different hardware via "execution providers": CPU, CUDA, CoreML, OpenVINO, TensorRT, etc. On any hardware it knows about, it'll pick the most efficient implementation.

What "dynamic" vs "static" quantization means

Dynamic: weights are quantized to INT8 ahead of time; activations are quantized on the fly each time the model runs. No calibration data needed. Easy. Sometimes works.

Static: both weights and activations are pre-quantized using statistics gathered from a representative set of input images ("calibration data"). More involved. Usually faster and more accurate than dynamic.

We used dynamic in this project. Static would be a Phase 6.

What a multi-stage Docker build buys you

Before multi-stage, the standard pattern was: one Dockerfile, one image, everything baked in. That meant the build tools, compilers, pip caches, and intermediate files all ended up in your production image. A multi-stage build lets you do the building in one image and then copy just the artifacts you need into a clean second image. Smaller images, fewer attack surfaces, faster deploys.

9. How to run each phase

From /Users/shashi/Desktop/ML Ops/:

# One-time setup
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

# Drop 2-3 photos with people/cars/animals in data/samples/

# Phase 1: PyTorch baseline
python -m scripts.phase1_baseline

# Phase 2: ONNX export, then parity check
python -m scripts.phase2_export_onnx
python -m scripts.phase2_parity

# Phase 3: optimize + quantize, then benchmark
python -m scripts.phase3_optimize
python -m scripts.phase3_benchmark

# Phase 4: containerized service
pip install -r requirements-inference.txt   # if you want to smoke-test locally first
docker compose up --build
curl -F "image=@data/samples/your_image.jpg" http://localhost:8000/predict
Things that might go wrong (and how to handle them):
  • Slow first run. Weight download takes ~30 seconds. Subsequent runs reuse the cache.
  • No detections. Drop the threshold by passing score_threshold=0.3 when calling predict().
  • Wrong labels (e.g. horse on a person photo). SSDLite is the smallest detector torchvision ships. We chose it for speed; accuracy is what it is.
  • Import errors. Use python -m scripts.foo, not python scripts/foo.py. The -m form sets up the import paths correctly.
  • Docker daemon not running. Start Docker Desktop. On macOS: open -a Docker, wait 30 seconds.
